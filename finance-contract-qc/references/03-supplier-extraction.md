# 03 · 供应商名称与账号提取

> 覆盖 workflow 步骤 5：从合同/补充协议中提取供应商名称与账号，并完成配对和清洗。

## 本文包含

- 目标与输入输出
- OCR 先行流程：PDF 转图、OCR、结构化提取、失败降级
- 供应商名称提取优先级（P0/P1/P2）
- 供应商账号提取与排除项
- 名称过滤、配对、多账号拆分、提取后清洗
- 对应节点与易错点

## 目标

从合同 / 合同补充协议中提取「供应商名称 + 供应商账号」对。先用 OCR 把页面图转成文本，再由大模型做结构化提取。一个文件可以产出多条记录；没有账号时账号留空字符串。

## 输入与输出

```json
// 输入：文件 URL 数组
["https://.../supplement-1.pdf", "https://.../supplement-2.jpg"]

// 输出：每个文件一条结果，columns 内是提取到的记录
[
  {
    "url": "https://.../supplement-1.pdf",
    "columns": [
      { "供应商名称": "杭州云智数据服务有限公司", "供应商账号": "110012345678" }
    ]
  }
]
```

后续清理节点会把每个文件的 `columns` 展开成扁平的「一条记录 + 来源 URL」列表。

这个 `[{ url, columns }]` 结构可以直接作为 `scripts/match.mjs` 的 `supplements` / `contracts` 输入，不需要再手写一遍配对和清洗。

## 提取流程（OCR 先行）

供应商提取分三步：**页面图 → OCR 文本 → 大模型结构化提取**。

原 workflow 是让视觉模型直接读页面图；本 skill 增加 OCR 前置步骤，用来降低长数字账号的误读率，业务规则不变。

```text
PDF/图片
  → pdf2img.mjs（PDF 时）
  → ocr-images.mjs
  → 页面 .txt + 合并 .txt
  → 大模型从 OCR 文本提取供应商名称/账号
  → 规则校验、清洗、配对
```

### 文件类型路由

| 类型 | 处理 |
|------|------|
| `.pdf` | `pdf2img.mjs` 转页面图 → `ocr-images.mjs` OCR → 大模型从 OCR 文本提取 |
| `.png` / `.jpg` / `.jpeg` | 直接 `ocr-images.mjs` OCR → 大模型提取 |
| 其他文档 | 先解析文本；没有文本层时转页面图再 OCR → 大模型提取 |
| OCR 失败 | 回退：把页面图交给视觉模型直接提取；仍失败则字段留空 |

分类步骤仍可直接用视觉模型看页面图；OCR 文本主要用于**供应商名称/账号提取**，避免长数字靠视觉模型硬读。

### 1. PDF 转页面图

复用 `references/02-merge-and-classify.md` 的「PDF 转图片」小节和 `scripts/pdf2img.mjs`，不要在本步骤重复实现。

```bash
node "<SKILL_DIR>/scripts/pdf2img.mjs" "<pdf-url-or-path>" \
  -o "<work-dir>/<doc-name>-images" \
  --scale 2 --format png
```

保留脚本输出的 `outDir` 和 `files`；OCR 直接对这批页面图运行。多页 PDF / 多张图片按**同一份文档**处理，不要逐页各提一份然后互相覆盖。

### 2. 页面图 → OCR 文本

```bash
node "<SKILL_DIR>/scripts/ocr-images.mjs" "<image-dir>" --out "<ocr-dir>"
```

默认配置：

- 端点：`http://new-api.crb.cn/v1/chat/completions`
- 模型：`财务领域-AI质检-qwen3.5-ocr`
- API Key：`DASHSCOPE_API_KEY`（或 `QWEN_OCR_API_KEY`）

默认端点是内网代理；如果不是可信网络，请用 `QWEN_OCR_ENDPOINT` 改成 HTTPS 端点，避免 API Key 明文传输。

常用选项：`--model`、`--endpoint`、`--api-style auto|native|openai`、`--prompt`、`--timeout`、`--max-image-bytes`、`--no-combine`、`--combined`。

输出：

- 在 `--out` 指定的输出目录生成 `<image-name>.txt`；
- 默认生成合并文件 `<name>-ocr.txt`，页与页之间用 `===== <image-name> =====` 分隔；
- stdout 打印 JSON，关键字段：`files`、`combinedFile`、`errors`、`successCount`、`failureCount`。

OCR 文本要保留页码/文件分隔符，不要把多份文档直接拼成一整段。OpenAI 兼容端点下，超过 `--max-image-bytes`（默认 700000）的图片会自动压缩为 JPEG，避免 `413`；压缩依赖 `sips`（macOS）或 ImageMagick `magick`，都没有时用 `--scale 1` 或 `--format jpg` 重新转图。

### 3. OCR 文本 → 供应商提取

把同一个文件的 OCR 文本（优先用 `combinedFile`，保留页分隔）交给大模型，按本文件的 P0/P1/P2、过滤词、配对和账号规则提取。

- **主输入是 OCR 文本**；页面图只用于核对版面、表格行和歧义位置。
- 要求模型输出 `{ "供应商名称": "...", "供应商账号": "..." }`；内部可额外记录来源页、原文引文和 `confidence`。
- 如果 OCR 文本与页面图冲突，不要猜：标记不确定，字段留空，按 `references/05-comparison.md` 的空值口径处理。
- 账号必须做纯数字、长度和排除项校验，不能直接把 OCR 结果当最终值。

### 4. OCR 失败/未配置

- 没有 `DASHSCOPE_API_KEY` 或未配置端点：先尝试视觉模型直接读页面图；仍不可用则字段留空，并在问题描述里说明 OCR 未执行。
- 单页 OCR 失败但其他页成功：保留成功页文本，失败页用页面图回退；不要因为一页失败丢掉整份文档。
- 全部 OCR 失败：按“附件不可读”处理，不要伪造名称或账号。

## 供应商名称提取优先级

按 P0 → P1 → P2，命中即停止：

### P0 · 专用 / 监管账户

标签包含以下任意关键词时，提取标签后的完整专户名称：

- 专用账户
- 监管账户
- 保证金账户
- 工资专户

示例：

```text
农民工工资专用账户：深圳市XXX司年产30万千升啤酒新建项目农民工工资专用账户
→ 供应商名称 = 深圳市XXX司年产30万千升啤酒新建项目农民工工资专用账户
```

专户名称必须**整段保留**，不要截断成公司名。

### P1 · 明确户名标签

标签为以下任意一种时，取标签后的值：

- 户名
- 收款方
- 销售方
- 开户名
- 全称

### P2 · 公司法定名称

以上标签都不存在时，取与账号语义最近、带公司后缀的全称：

- 有限公司
- 集团
- 厂
- 局

### 排除项

- 自然人姓名
- 不含「账户 / 专户」字样的纯项目名称
- 品牌简称

## 供应商账号提取

### 合法格式

- 连续纯数字字符串；
- 允许中间有空格或连字符，输出时去掉。

### 必须出现在账户语境

账号附近要出现以下关键词之一：

- 账号
- 专户账号
- 收款账号
- 银行卡号

### 严格排除

- 印章 / 签章区数字
- 统一社会信用代码 / 税号（含字母，或 91 / 92 开头）
- 发票代码
- 订单号
- 电话
- 身份证号
- 内部流水号
- 防伪码
- 页眉页脚水印数字

## 名称过滤规则（最高优先级）

在配对前执行。命中即丢弃该条记录，不输出：

- 账户户名包含 `雪花`、`金沙`、`酒业`（不区分大小写）；
- 结合图文判断属于水印、测试数据或非真实交易主体。

这三个词是**付款方/酒业内部主体**的识别词，不是白名单。不要把「贵州金沙窖酒酒业有限公司」当成供应商。

## 配对规则

1. **就近绑定**：每个有效户名与语义最近、且合法的账号配对；优先同一行、同一语义块。
2. **禁止跨段匹配**：户名和账号在相邻行或同一表格行时，不得跳到远处找另一个公司的账号。
3. **多账号拆分**：账号用 `/`、`、` 或换行分隔时，拆成多条记录，户名相同、账号不同。
4. **无账号**：户名合法但附近没有有效账号时，账号返回 `""`，不要丢记录。

示例：

```text
收款方：杭州云智数据服务有限公司
账号：110012345678 / 110087654321
→ [
  { "供应商名称": "杭州云智数据服务有限公司", "供应商账号": "110012345678" },
  { "供应商名称": "杭州云智数据服务有限公司", "供应商账号": "110087654321" }
]
```

## 提取后的清洗

对每条记录的名称和账号再做一次清洗，规则同 `references/01-input-and-normalization.md`：

- 名称：去空白、括号、引号、连字符、标点，只保留中英文和数字；
- 账号：去各种减号、空白、括号、标点。

OCR 文本常见的断行、空格、全角符号也在这里统一处理。清洗后还要做一次校验：

- 账号必须是纯数字（或纯数字加字母，如果业务确实允许）；
- 账号长度要符合银行账号的常见范围，明显过短/过长的丢弃；
- 再次排除税号、发票代码、订单号、电话、身份证号、印章数字；
- 名称不能只剩“有限公司”“账户”等残片，残片按空值处理。

清洗后名称为空、账号为空的记录先保留，交给 `references/04-whitelist-and-branching.md` 的去空/合并步骤统一处理。

### 交给 match.mjs 前的硬校验

`scripts/match.mjs` 会在清洗后再校验一次，不通过时按「不可用」处理，不会静默当空值放行：

- 账号长度 6–32；默认拒绝字母（`--allow-alphanumeric-accounts` 可放开）；
- 18 位且以 `91` / `92` 开头，按统一社会信用代码拒绝；
- 名称只剩「有限公司」「账户」「专户」等残片时按空值处理；
- 记录带 `confidence` 且低于阈值（默认 `0.6`）时，非空字段按不可用处理。

因此提取时建议每条记录附一个 `confidence`（0–1）；不附则跳过置信度校验。

## 易错点

- 不要把税号、发票代码、电话当账号；账号必须在「账号/收款账号/银行卡号」语境里。
- 不要因为名称里含「金沙」就一律丢弃；过滤词针对的是**供应商户名**，不是报账单付款方。
- 专户名称要整段保留，截成公司名会与报账单户名对不上。
- 多页文档要合并理解，不能第一页提名称、第二页提账号后互相当成两份记录。
- 名称和账号必须就近配对；跨段配对会造成「名称对、账号对，但不是同一家」的假 PASS。
- 不要直接把 OCR 数字当最终账号；OCR 可能漏位/错位，必须做长度和排除项校验。
- 不要把多份文档的 OCR 文本拼成一整段；保留 `===== <image-name> =====` 页分隔。
- 不要把印章、页眉页脚、二维码附近的数字当成账号。
