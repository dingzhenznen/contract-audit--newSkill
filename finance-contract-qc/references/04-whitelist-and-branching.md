# 04 · 白名单与补充协议分流

> 覆盖 workflow 步骤 6 + 7：先做白名单短路，再按补充协议数量决定提取与比对路径。

## 本文包含

- 一、白名单短路：关键词、长度阈值、PASS 输出
- 二、补充协议分流：1 份 / 多份 / 0 份、合并算法、合同回填与二次判定、任意一条匹配

## 一、白名单短路

### 目标

在读取任何合同附件之前，先用报账单户名做一次短路判断。命中白名单或名称过短，直接输出 PASS，不再进入附件合并、分类和提取。

### 位置

```
步骤 4 报账单字段提取
  → 步骤 6 白名单判断
      ├─ 命中 → 直接 PASS
      └─ 未命中 → 步骤 2 合并 → 步骤 3 分类 → 步骤 5 提取 → 步骤 7/8 分流与比对
```

白名单判断使用的是**清洗后的报账单户名** `account_name`。

### 判定规则

按顺序执行：

```js
if (!name) return false;                 // 空名称不命中
if (白名单关键词.some(k => name.includes(k))) return true;
if (name.length < 4) return true;         // 清洗后长度小于 4
return false;
```

#### 白名单关键词

名称包含以下任意一个关键词即命中：

- `国网`
- `电网`
- `中国电信`
- `中国移动`
- `中国石油天然气`
- `中国联合网络通信`
- `中国石化`

#### 长度阈值

- 清洗后名称长度 **< 4** 即命中。
- 按 JavaScript 字符串长度计算，一个汉字算 1。
- 清洗已去掉空格、括号、标点，所以「国网 河南」与「国网河南」等价。

### PASS 输出

命中后只输出判断结果，问题列表为空：

```json
{
  "判断结果": [
    {
      "稽核行号": 1,
      "判断结果": "PASS"
    }
  ],
  "问题列表": []
}
```

不需要读取附件，不需要写问题描述，不需要附来源链接。

### 示例

| 报账单户名 | 清洗后 | 判定 | 原因 |
|------------|--------|------|------|
| 国网河南省电力公司 | 国网河南省电力公司 | PASS | 含「国网」 |
| 中国移动通信集团河南有限公司 | 中国移动通信集团河南有限公司 | PASS | 含「中国移动」 |
| 中国石油天然气股份有限公司 | 中国石油天然气股份有限公司 | PASS | 含「中国石油天然气」 |
| 水务局 | 水务局 | PASS | 长度 3 < 4 |
| 金沙县水务局 | 金沙县水务局 | 不命中 | 长度 6，且不含白名单词 |
| 河南和之也商贸有限公司 | 河南和之也商贸有限公司 | 不命中 | 长度 ≥ 4，不含白名单词 |

### 与提取过滤词的区别

| 列表 | 用途 | 词 |
|------|------|----|
| 白名单 | 报账单户名命中后直接 PASS | 国网、电网、中国电信、中国移动、中国石油天然气、中国联合网络通信、中国石化 |
| 提取过滤词 | 供应商户名命中后丢弃该条记录 | 雪花、金沙、酒业 |

两张表不能混用：前者是「报账单付款方」，后者是「合同供应商户名」。

### 对应节点

- `zfYLpca5CK9zv7HQ` 供应商名称白名单
- `iiIiHrMpba4UhuRG` 判断器#13
- `d0laRDtyKDOWKjrX` 指定回复#7

### 易错点

- 名称为空时**不命中**白名单，继续走附件流程；不要因为空名称就 PASS。
- 不要把「白名单」理解为「所有国企/事业单位」；只认这 7 个关键词和长度阈值。
- 长度阈值是清洗后的长度，不是原始长度；带括号、空格的名称先去符号再算。
- 命中白名单后不要再读合同，避免无意义的附件下载和识别。

## 二、补充协议数量分流与合同回填

> 本节的分流、合并、回填和比对已实现为 `scripts/match.mjs`。规则有歧义时以本文为准；跑结果时优先用脚本，避免模型每次执行产生差异。

### 目标

根据「合同补充协议」的数量决定提取路径：

- 1 份：直接提取、直接比对；
- 多份：先清洗、去空、合并，再比对；
- 0 份：回退到「合同」。

补充协议优先；补充协议缺名称或账号时，用合同同名信息补缺。

### 两个文件列表

```text
S = 文件分类结果["合同补充协议"]  // 可能是 []
C = 文件分类结果["合同"]          // 可能是 []
```

### 总决策树

```text
                ┌─ |S| == 1 ─→ 提取 1 份补充协议
                │                ├─ 记录数 > 1 → 任意一条匹配
                │                └─ 记录数 ≤ 1 → 名称/账号齐全？
                │                                   ├─ 是 → 直接比对
                │                                   └─ 否 → 合同回填
                │
S 的数量 ───────┼─ |S| > 1  ─→ 提取全部补充协议 → 清洗/去空/合并
                │                ├─ 合并后 > 1 条 → 任意一条匹配
                │                └─ 合并后 ≤ 1 条 → 齐全？
                │                                   ├─ 是 → 直接比对
                │                                   └─ 否 → 合同回填
                │
                └─ |S| == 0 ─→ 看 C
                                 ├─ |C| == 1 → 提取合同
                                 ├─ |C| > 1  → 清洗/去空/合并
                                 └─ |C| == 0 → 无附件，空值兜底
```

### 分支一：只有 1 份补充协议

1. 调文件信息提取，得到该协议的所有记录。
2. 如果记录数 > 1：直接进入「任意一条匹配」。
3. 如果记录数 == 0：直接进入「合同回填」。
4. 如果记录数 == 1：取第一条记录。
   - 名称和账号都非空 → 直接进入严格比对。
   - 任一为空 → 保留已有值，进入「合同回填」。

注意：单份协议内部有多条记录时，**不做合并**，直接任意一条匹配；这与多份协议的处理不同。

### 分支二：多份补充协议

1. 对每份协议分别提取，得到多条记录。
2. 清洗每条记录的名称和账号。
3. 去空：名称和账号都为空白的记录丢弃。
4. 合并同义记录（算法见下）。
5. 合并后：
   - 记录数 > 1 → 任意一条匹配；
   - 记录数 == 1 → 取第一条；名称/账号任一为空则进入合同回填；
   - 记录数 == 0 → 直接进入合同回填。

#### 合并算法

两条记录可以合并，当且仅当每个字段满足「相等或至少一方为空」：

```js
canMerge =
  (!currentName    || !groupName    || currentName    === groupName) &&
  (!currentAccount || !groupAccount || currentAccount === groupAccount);
```

合并时保留**非空字段更多**的那条：

```js
if (currentNonEmptyCount > groupNonEmptyCount) {
  group = currentRecord;
}
```

无法合并时，新建一组。

示例：

```text
记录1：名称=A，账号=""      ┐
记录2：名称="", 账号=6222…  ┘ 可合并，但两者各只有 1 个非空字段
                              → 保留先出现的记录1，账号 6222… 被丢弃

记录1：名称=A，账号=""      ┐
记录2：名称=B，账号=""      ┘ 名称不同 → 不合并，保留两组
```

> 这个算法**不做字段级互补拼接**，只决定「谁留下」。因此只有名称和只有账号的两条记录，非空字段数相等时会丢掉后一条的另一半。这是工作流的既有行为，`scripts/match.mjs` 原样实现；如果业务要求互补，必须先改工作流再改脚本，不能只改文档。

### 分支三：没有补充协议，回退合同

1. 取 `C`（合同列表）。
2. `|C| == 0`：没有任何可用合同附件，全局名称/账号保持空值，直接进入空值容忍分支（`执行质检#10`，见 `references/05-comparison.md`）。
3. `|C| == 1`：提取该合同，再按记录数分流（`判断器#15`）。
4. `|C| > 1`：逐份提取，清洗、去空、合并，再按记录数分流（`判断器#16`）。

合同提取的规则与补充协议完全一致，见 `references/03-supplier-extraction.md`。提取后的回填与二次判定见下节。

### 合同回填与二次判定

原则：补充协议优先，合同只补空缺。回填分三步，不能跳过第二步直接比对。

#### 第一步：把补充协议的值写入全局

`判断器#4` / `判断器#6` 判定「名称或账号有空」后，`变量更新` / `变量更新#2` 会把该条记录的名称、账号、来源 URL 整体写入全局变量，然后才进入合同提取。字段为空也照写，空缺留给合同补。

#### 第二步：按记录形态回填

单条记录和多条记录的回填语义不同，不能合并成一套：

| 路径 | 触发 | 回填方式 | 节点 |
|------|------|----------|------|
| 单条记录 | 单份合同 ≤1 条；或多份合同合并后 ≤1 条 | **只填空**：全局字段为空且记录有值才写入 | `判断器#8`→`变量更新#3`、`判断器#9`→`变量更新#4`、`判断器#11`→`变量更新#5`、`判断器#12`→`变量更新#6` |
| 多条记录 | 单份合同 >1 条；或多份合同合并后 >1 条 | **整体覆盖**：全局字段非空时，改写每一条记录的同名字段 | `代码运行#14`（扁平键）、`代码运行#15`（`columns` 结构） |

整体覆盖的含义是：补充协议的值优先于合同里的不同值。例如补充协议名称=A，合同记录里出现 B，覆盖后全部变成 A，再按「任意一条」比对。

`代码运行#14` 只处理 `供应商名称` / `供应商账号` 两个扁平键；`代码运行#15` 处理 `columns["供应商名称"]` / `columns["供应商账号"]`，并同步 `url`。

#### 第三步：选择空值口径

回填完成后，两条路径的判定方式不同：

| 路径 | 回填后状态 | 使用的提示词 | 空值口径 |
|------|------------|--------------|----------|
| 单条记录 | 名称、账号都非空 | `执行质检#4` / `执行质检#6` | 严格，按字面比较 |
| 单条记录 | 任一为空 | `执行质检#10`（`uXHCwmNyAhHUT3Xd`） | 容忍，空字段视为无误 |
| 多条记录 | 不再检查，直接比对 | `执行质检#10`（`hzTWeUdGhvniq7pn`）/ `执行质检#5` | 严格，按字面比较 |
| 无合同（`C` 为空） | 不经过回填 | `执行质检#10`（`uXHCwmNyAhHUT3Xd`） | 容忍，空字段视为无误 |

关键差异：**只有单条记录路径会做二次空值检查**。多条记录路径在覆盖后直接进入严格提示词，不会因为字段为空而切换到容忍分支。

因此「合同里没有账号」不等于「账号不一致」：

- 单条记录：切到容忍分支，账号不判错；
- 多条记录：仍按字面比较，空值可能被判为不一致。

不要在这一步沿用补充协议阶段的「字段齐全」口径，也不要全局套用严格分支。

#### URL 规则

来源 URL 跟着字段走：名称来自补充协议就记补充协议 URL，账号来自合同就记合同 URL。

`代码运行#15` 在多条记录覆盖时，如果名称和账号都有值且来源 URL 不同，**以账号来源 URL 为准**。

### 任意一条匹配

合并后有多条记录时，报账单的「名称 + 账号」只要与**任意一条记录**同时相等，即视为匹配。

不要先把多条记录拼成一个字符串再整体比较；那样只能得出「不一致」，也无法定位是哪一条。

### 易错点

- 不要把多份协议的名称和账号分别拼成两个大字符串；必须保留记录结构。
- 不要在多份协议合并后丢掉来源 URL；问题描述需要指向具体附件。
- 单份协议多记录与多份协议的处理不同：前者不合并，后者先合并。
- 补充协议字段为空不等于「一致」；先回填，再按「单条记录二次判定 / 多条记录直接严格」选择口径。
- 不要把单条记录的「只填空」套到多条记录上；多条记录是全局值整体覆盖每一条。
- 不要漏掉回填后的二次判定；合同缺字段时单条记录会切到 `执行质检#10`，该字段不判错。
- 合并不是互补拼接：非空字段数相等时保留先出现的记录，后一条的另一半会丢失。
