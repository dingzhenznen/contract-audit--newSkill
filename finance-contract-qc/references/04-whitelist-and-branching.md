# 04 · 白名单与补充协议分流

> 覆盖 workflow 步骤 6 + 7：先做白名单短路，再按补充协议数量决定提取与比对路径。

## 本文包含

- 一、白名单短路：关键词、长度阈值、PASS 输出
- 二、补充协议分流：1 份 / 多份 / 0 份、合并算法、合同补缺、任意一条匹配

## 一、白名单短路

### 目标

在读取任何合同附件之前，先用报账单户名做一次短路判断。命中白名单或名称过短，直接输出 PASS，不再进入附件合并、分类和提取。

### 位置

```
步骤 4 报账单字段提取
  → 步骤 6 白名单判断
      ├─ 命中 → 直接 PASS
      └─ 未命中 → 步骤 2 合并 → 步骤 3 分类 → 步骤 5 提取 → 步骤 7/8 分流与比对
```

白名单判断使用的是**清洗后的报账单户名** `account_name`。

### 判定规则

按顺序执行：

```js
if (!name) return false;                 // 空名称不命中
if (白名单关键词.some(k => name.includes(k))) return true;
if (name.length < 4) return true;         // 清洗后长度小于 4
return false;
```

#### 白名单关键词

名称包含以下任意一个关键词即命中：

- `国网`
- `电网`
- `中国电信`
- `中国移动`
- `中国石油天然气`
- `中国联合网络通信`
- `中国石化`

#### 长度阈值

- 清洗后名称长度 **< 4** 即命中。
- 按 JavaScript 字符串长度计算，一个汉字算 1。
- 清洗已去掉空格、括号、标点，所以「国网 河南」与「国网河南」等价。

### PASS 输出

命中后只输出判断结果，问题列表为空：

```json
{
  "判断结果": [
    {
      "稽核行号": 1,
      "判断结果": "PASS"
    }
  ],
  "问题列表": []
}
```

不需要读取附件，不需要写问题描述，不需要附来源链接。

### 示例

| 报账单户名 | 清洗后 | 判定 | 原因 |
|------------|--------|------|------|
| 国网河南省电力公司 | 国网河南省电力公司 | PASS | 含「国网」 |
| 中国移动通信集团河南有限公司 | 中国移动通信集团河南有限公司 | PASS | 含「中国移动」 |
| 中国石油天然气股份有限公司 | 中国石油天然气股份有限公司 | PASS | 含「中国石油天然气」 |
| 水务局 | 水务局 | PASS | 长度 3 < 4 |
| 金沙县水务局 | 金沙县水务局 | 不命中 | 长度 6，且不含白名单词 |
| 河南和之也商贸有限公司 | 河南和之也商贸有限公司 | 不命中 | 长度 ≥ 4，不含白名单词 |

### 与提取过滤词的区别

| 列表 | 用途 | 词 |
|------|------|----|
| 白名单 | 报账单户名命中后直接 PASS | 国网、电网、中国电信、中国移动、中国石油天然气、中国联合网络通信、中国石化 |
| 提取过滤词 | 供应商户名命中后丢弃该条记录 | 雪花、金沙、酒业 |

两张表不能混用：前者是「报账单付款方」，后者是「合同供应商户名」。

### 易错点

- 名称为空时**不命中**白名单，继续走附件流程；不要因为空名称就 PASS。
- 不要把「白名单」理解为「所有国企/事业单位」；只认这 7 个关键词和长度阈值。
- 长度阈值是清洗后的长度，不是原始长度；带括号、空格的名称先去符号再算。
- 命中白名单后不要再读合同，避免无意义的附件下载和识别。

## 二、补充协议数量分流与合同补缺

### 目标

根据「合同补充协议」的数量决定提取路径：

- 1 份：直接提取、直接比对；
- 多份：先清洗、去空、合并，再比对；
- 0 份：回退到「合同」。

补充协议优先；补充协议缺名称或账号时，用合同同名信息补缺。

### 两个文件列表

```text
S = 文件分类结果["合同补充协议"]  // 可能是 []
C = 文件分类结果["合同"]          // 可能是 []
```

### 总决策树

```text
                ┌─ |S| == 1 ─→ 提取 1 份补充协议
                │                ├─ 记录数 > 1 → 任意一条匹配
                │                └─ 记录数 ≤ 1 → 名称/账号齐全？
                │                                   ├─ 是 → 直接比对
                │                                   └─ 否 → 合同补缺
                │
S 的数量 ───────┼─ |S| > 1  ─→ 提取全部补充协议 → 清洗/去空/合并
                │                ├─ 合并后 > 1 条 → 任意一条匹配
                │                └─ 合并后 ≤ 1 条 → 齐全？
                │                                   ├─ 是 → 直接比对
                │                                   └─ 否 → 合同补缺
                │
                └─ |S| == 0 ─→ 看 C
                                 ├─ |C| == 1 → 提取合同
                                 ├─ |C| > 1  → 清洗/去空/合并
                                 └─ |C| == 0 → 无附件，空值兜底
```

### 分支一：只有 1 份补充协议

1. 调文件信息提取，得到该协议的所有记录。
2. 如果记录数 > 1：直接进入「任意一条匹配」。
3. 如果记录数 == 0：直接进入「合同补缺」。
4. 如果记录数 == 1：取第一条记录。
   - 名称和账号都非空 → 直接进入严格比对。
   - 任一为空 → 保留已有值，进入「合同补缺」。

注意：单份协议内部有多条记录时，**不做合并**，直接任意一条匹配；这与多份协议的处理不同。

### 分支二：多份补充协议

1. 对每份协议分别提取，得到多条记录。
2. 清洗每条记录的名称和账号。
3. 去空：名称和账号都为空白的记录丢弃。
4. 合并同义记录（算法见下）。
5. 合并后：
   - 记录数 > 1 → 任意一条匹配；
   - 记录数 == 1 → 取第一条；名称/账号任一为空则进入合同补缺；
   - 记录数 == 0 → 直接进入合同补缺。

#### 合并算法

两条记录可以合并，当且仅当每个字段满足「相等或至少一方为空」：

```js
canMerge =
  (!currentName    || !groupName    || currentName    === groupName) &&
  (!currentAccount || !groupAccount || currentAccount === groupAccount);
```

合并时保留**非空字段更多**的那条：

```js
if (currentNonEmptyCount > groupNonEmptyCount) {
  group = currentRecord;
}
```

无法合并时，新建一组。

示例：

```text
记录1：名称=A，账号=""      ┐
记录2：名称="", 账号=6222…  ┘ 可合并 → 名称=A，账号=6222…

记录1：名称=A，账号=""      ┐
记录2：名称=B，账号=""      ┘ 名称不同 → 不合并，保留两组
```

> 这个算法的副作用是：只有名称的记录可能和只有账号的记录配成一对，即使它们来自不同协议。业务上应优先让同一份协议内的名称和账号配对；跨协议合并只在字段确实互补时使用。

### 分支三：没有补充协议，回退合同

1. 取 `C`（合同列表）。
2. `|C| == 1`：提取该合同。
3. `|C| > 1`：逐份提取，再清洗、去空、合并，规则同上。
4. `|C| == 0`：没有任何可用合同附件，供应商名称/账号保持空值，进入空值兜底（见 `references/05-comparison.md`）。

合同提取的规则与补充协议完全一致，见 `references/03-supplier-extraction.md`。

### 合同补缺

补充协议优先。若补充协议只提供了名称或只提供了账号：

1. 先把已有值写入全局供应商变量（名称、账号、来源 URL）。
2. 再提取合同。
3. 只填充**仍为空**的字段：

```text
名称：补充协议有值 → 保留；为空 → 用合同名称
账号：补充协议有值 → 保留；为空 → 用合同账号
```

4. 两个字段都齐后进入比对；仍不齐则进入空值兜底。

来源 URL 也要跟着字段走：名称来自补充协议就记补充协议 URL，账号来自合同就记合同 URL。

### 任意一条匹配

合并后有多条记录时，报账单的「名称 + 账号」只要与**任意一条记录**同时相等，即视为匹配。

不要先把多条记录拼成一个字符串再整体比较；那样只能得出「不一致」，也无法定位是哪一条。

### 易错点

- 不要把多份协议的名称和账号分别拼成两个大字符串；必须保留记录结构。
- 不要在多份协议合并后丢掉来源 URL；问题描述需要指向具体附件。
- 单份协议多记录与多份协议的处理不同：前者不合并，后者先合并。
- 补充协议字段为空不等于「一致」；要先用合同补缺，再按空值口径判断。
- 合并时「空值可匹配」可能把不同协议的名称和账号配到一起；优先同协议配对，跨协议只补缺。
