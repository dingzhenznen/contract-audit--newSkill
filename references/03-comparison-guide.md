# 03 · 比对与判级

## 1. 比对三段式

任何一次比对都要能回答三个问题（都要落进内部留痕，不输出）：

```
原文 → 归一化 → 判定
```

1. 合同侧**原文**是什么？
2. 表单侧**原文**是什么？
3. 归一化之后，**为什么**判成这个结果？

只有结论没有过程，等于没有审计。

---

## 2. 三种比对模式

### 2.1 单值比对（EXACT_NORMALIZED）

适用：经销商名称、终端名称、协议有效期、合作方式、其他折扣。

```
L1 空白 + L2 全半角 + L3 大小写（+ 按字段追加 L4/L5/L6）
归一化后完全相等 → 一致（通过）
否则              → 不一致（取该条 judgeRule 的等级）
```

示例：
- 合同 `甲方（供货方）：河南和之也商贸有限公司` → 取 `河南和之也商贸有限公司`
- 表单 `customerName = "河南和之也商贸有限公司"`
- L1/L2 后相等 → 一致 → `通过`

### 2.2 数值比对（NUMERIC）

适用：进店价、零售价、预计销量。

```
L5 归一化为数值 → 判 |a - b| ≤ tolerance
```

**容差默认 0**（规则集没写容差就严格相等）。`3.80` 与 `3.8` 经 L5 后相等；`66` 与 `60` 不等。

### 2.3 行级集合比对（ROW_SET）—— 表格类规则必用

```
① 两侧各自构建 {key → row}
   合同侧 key = 产品品种（表格第 1 列）
   表单侧 key = products[].productName
② key 归一化后配对（见 §3）
③ 分三类处理：
   ├─ 双侧都有 → 逐列比对：全部相等 → 一致；任一列不等 → 不一致
   ├─ 仅合同有 → 不一致（表单漏报）
   └─ 仅表单有 → 不一致
④ 规则级结论 = 各行的"最高档"，只要有一行不一致，该条就不通过
```

**行级结论必须定位到行**：`auditDesc` 里要能直接看到"哪个产品的合同值 vs 表单值"。

## 3. 行主键配对：合同简称 ↔ 表单全称 SKU

这是本项目最容易配错的地方。两张表的商品命名粒度**天然不同**：

| 合同「产品品种」（简称） | 表单 `productName`（全称 SKU） |
|---|---|
| 喜力星银 | 喜力silver9.5度500ml统一标准专用绿瓶1*12纸箱含瓶 |
| 老雪 | 雪花经典(老雪)12度640ml统一标准专用棕瓶1*12纸箱含瓶 |
| 雪花纯生/红爵 | 雪花纯生8度500ml白瓶1*12纸箱 |
| 勇闯天涯superX | 勇闯天涯superX9度500ml雪花统一标准专用蓝瓶1*12纸箱 |
| 勇闯天涯 | 雪花勇闯天涯(2021版)8度500ml统一标准专用白瓶1*12塑箱 |

**字面主键配对会全部落空**（5 行 `ROW_MISSING_IN_FORM` + 8 行 `ROW_MISSING_IN_CONTRACT`），这显然是命名粒度问题而不是真实差异。处理方法：

```
① 按「品牌 + 系列」做语义映射：合同简称的品牌词是否出现在表单全称里
   喜力星银 → 喜力…；老雪 → 雪花经典(老雪)；雪花纯生/红爵 → 雪花纯生；…
② 语义映射必须做交叉验证：用金额/价格列反向确认映射方向
   （实测：5 行中 3 行的进货价精确吻合 85 / 85 / 68 → 映射成立）
③ 表单里 salesCount = 0 且无价格的行（未实际执行的新增 SKU）不参与行配对，
   但仍要在内部记下数量，避免"表单 8 行 vs 合同 5 行"被误判成漏签
④ 若语义映射无法建立（品牌词对不上、无法交叉验证）→ 如实按字面结果判定：
   合同行"仅合同有"、表单行"仅表单有"，两侧都算不一致
```

> 关键点：**语义映射与字面配对在本项目里结论一致** —— 两条价格型规则的 `judgeRule` 都是"不一致 → 高风险"，无论按哪种口径配对，只要有一处对不上就是高风险。所以优先用语义映射（能定位到具体产品），并在内部记下另一种口径的结果。

## 4. 单位口径：零售价 元/瓶 ↔ 元/件

| 侧 | 列名 / 字段 | 实际单位 |
|---|---|---|
| 合同 | 建议销售价（元） | **元/瓶**（规则 `helpDesc` 亦标注 `建议销售价(元/瓶)`） |
| 表单 | `products[].retailPrice` | **元/件**（= 元/瓶 × 件内瓶数） |

不进折算直接比，**每一行都会不一致**，这是系统性假阳性，必须处理：

```
折算倍数 = 件内瓶数，取自合同表格「规格」列：1*12 → 12
表单折算值 = retailPrice / 12    （例：144 → 12 元/瓶）
折同单位后再逐行比对
```

实测验证：喜力 144/12 = 12、纯生 120/12 = 10、superX 96/12 = 8 —— 与合同 12 / 10 / 8 精确吻合，确认换算方向正确；`勇闯天涯` 84/12 = 7 ≠ 合同 6，为真实不一致。

边界：若「规格」列缺失或不是 `1*N` 形式，无法确定倍数 → 按原始值比对（此时几乎必然全部不一致，需在内部标注"疑似单位口径差异"）。

**进店价（`entryPrice`）与合同「乙方进货价（元）」两侧同为元/件，不需换算。**

## 5. 判级（表驱动，唯一的等级来源）

```
比对状态 ──查该条 judgeRule──> 等级
不一致 ──> 该条 judgeRule 引号中的等级（高风险 / 中风险 / 低风险）
一致   ──> 通过
judgeRule 写"不判断" ──> 通过（auditDesc 留空）
```

- **不合并、不升级、不降级。** 不许因为"价格问题看着更严重"把中风险提成高风险，也不许因为"影响不大"降档。
- 本项目规则集**不区分**"值不同 / 行缺失 / 合同侧为空 / 锚点未命中"这几种情形 —— 全部落同一档。
- 整体 `riskLevel` = 所有 `checkRes` 的最高档（`高风险 > 中风险 > 低风险 > 通过`）。
  例：`[中风险, 低风险, 低风险]` → `中风险`；`[高风险, 中风险]` → `高风险`；全部 `通过` → `通过`。

## 6. 比对自查

- [ ] 每条件比对都记录了 原文 → 归一化 → 结论 三层（内部留痕）
- [ ] 归一化层数可解释（判一致时能说出经过哪几层）
- [ ] 数值容差来自规则集，未擅自放宽（默认 0）
- [ ] 表格类规则输出到了行，不是只给一个总体结论
- [ ] 行配对用了归一化/语义映射的 key，但 `auditDesc` 里写的是原文
- [ ] 等级全部来自 `judgeRule`，无临场发明
- [ ] 单位换算只用在零售价（元/瓶 ↔ 元/件）这一处，且有交叉验证
- [ ] 合同侧每页只读了一次；读不清的值走兜底取空，**未追加读图**（复读 / 放大 / 切片）
